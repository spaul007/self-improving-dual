Block-Tiered HGM — search mechanism

The tree of edits

Block-Tiered HGM doesn't rewrite a multi-agent system all at once — it grows a family tree of variants, one small edit at a time. Every branch point is the same two-part gamble: which variant is worth editing further, and which part of it to touch. Fitter branches get picked again and again; weaker ones stop getting picked, the same way a lineage that isn't reproducing simply stops showing up in the next generation.

Four generations, one surviving lineage

Illustrative tree, not measured data. Every chip has all four blocks — the filled quadrant is the one this edit touched; the other three carried straight over from the parent, untouched this round. The root is the unedited seed, so none of its quadrants are filled yet.

What happens at one branch point

Zooming into any single arrow in the tree above — this loop is what produces every new node.

01

Pick a parent

Every existing variant has some chance of being chosen, but ones with a higher score so far are favored — the way case 30 or 22 kept producing new children above.

02

Pick a block

One of four surfaces: one sub-agent's own prompt/logic, the hand-offs between stages, shared plumbing every stage relies on, or an output-checking stage.

03

Edit, then evaluate

An editor rewrites only that block of the parent's code. The resulting variant is a new node, run on real cases to get a score.

04

Feed the score back

The new score updates the odds that this exact node — or its parent's other children — gets picked again in step 1.

What the search carries forward

Neither of the two choices above is made from scratch each time. Two things persist across the whole tree — updated by every EVALUATE, consulted by the next EXPAND.

The four blocks

Same four surfaces, every generation — what changes is which one gets picked, and how often that choice pays off.

individual_subagent

One role's own prompt and behavior — what it's told, which tools it calls.

collaboration_workflow

How stages sequence and hand work to each other — who sees what, in what order.

foundation_capability

Shared substrate every role builds on — retries, timeouts, tool routing.

verifiers

A stage that checks the finished result against the real scoring rubric before it ships.
