Edit-Memory HGM Architecture

How the proposed edit-memory layer sits on the HGM tree search with the agentic editor: which arm each expansion takes, what the curators read, where the two textual variables (the memory B and the generator instruction I) are updated, and what every component can and cannot see.

1 · The loop with the memory layer attached

The HGM manager is unchanged in its regime: a scheduler alternates EXPAND and EVALUATE steps until the evaluation budget is spent. The edit-memory layer is an observer that hooks the same events the tree snapshotter already sees, and one extra input into EXPAND.

2 · One expansion: the two arms

An expansion always runs the same agentic editor session on a copy of the parent. The with-memory arm gets $EDIT_MEMORY_FILE bound read-only into its sandbox, a procedure step telling it to read it, and — because the memory cites node ids — the whole run readable regardless of the configured read_scope, so it can open the code and results of every node the memory refers to. The without-memory arm gets the byte-identical prompts of the finished no-editmem run under the configured scope. Both arms are denied the edit_memory/ directory itself.

3 · Cadence: windows, versions, arms

With window_size m = 4 and instruction_every n = 2 a 1000-eval run (~32 expansions) produces ~8 memory versions and ~4 instruction versions. Nodes 1–4 necessarily run without memory (arm none); from B1 on, the bandit chooses.

4 · Memory update: window → curator → generator

The curator is an agentic session with the same machinery as the editor (bash in bubblewrap, an editor tool, a submit tool), but a different read/write surface: it may read the m window nodes and their parents, and it may write only inside its own window directory. It reads what it wants — nothing is pre-digested for it.

5 · Instruction update as nested TextGrad

Two textual variables are optimized, one inside the other. Inner: the memory B (gradient Z from each window). Outer: the generator's instruction addendum I (gradient Q from how editors used the memory and how task agents fared). In TextGrad terms the curators are the backward pass and the two generator calls are textual-gradient-descent steps; the fixed core of I is the part TextGrad keeps constant.

Optional guard (not in v1): use the bandit's with-memory success rate over the window after Ik+1 as a validation signal and roll back to Ik if it drops. This is score-based, but at the manager level, so it does not put predictions into the memory.

6 · Bandit posterior per arm

Each arm's posterior is built from the same success/failure mass HGM already keeps per node, pooled over every node that was generated under that arm — no paired comparison, no reward shaping. The without arm pools every node expanded without the memory, including the ones from before B1 existed.

10 · What to evaluate in this design

  1. Arm isolation. The with arm differs by one file, one procedure step and full-run visibility; the without arm stays byte-identical to the finished run. Should the memory's guidance also enter the system prompt?
  2. Window semantics. Non-overlapping windows of m successful nodes; a window closes on the m-th paired evaluation regardless of how the scheduler interleaved top-ups. Alternative: close only when every member has ≥ k evals.
  3. What the curator is told to look at. The legend names all artifacts; the instruction asks for per-node sections plus a gradient against Bj. Is the "shortcomings: strategy vs implementation" split enough structure, or should the curator also produce the ranking?
  4. Ranking basis. The generator ranks by judged usefulness from Z; mean scores are shown to the curator as context only and never to the generator. Acceptable, or should even the curator be blind to means?
  5. Bandit posterior. Pooled HGM tallies per arm (same estimator as node selection); pre-B1 nodes count for without. Note the posterior compares the arms' descendants as populations, so parent quality is not factored out — accepted by design.
  6. Instruction scope. Ik only instructs the memory generator. Should the memory curator also read the addendum (so it curates what the generator will need)? Plan says yes, read-only.
  7. TextGrad discipline. Gradient sections in Z and Q, minimal-change optimizer steps, momentum from previous gradients. Rollback of I via the bandit signal is left out of v1.
  8. Cost and wall clock. ~8 curator sessions + ~4 instruction sessions per 1000-eval run, each comparable to an editor session; all run synchronously inside the loop.
  9. Read scope. The with-memory arm always gets the whole run (it must be able to open the nodes the memory cites); the configured read_scope governs only the without arm. Under parent scope the arms therefore also differ in cross-node visibility — acceptable, since the memory is what makes other nodes worth reading.
